### 3.2 优先级上限的确定性规则（不可由模型决定）

对应设计 §9.1。**代码执行上限，模型只能提议**：

| 条件 | 允许的研究优先级 |
| --- | --- |
| 请求在入队前被拒 | 无（不创建 run/case） |
| 身份冲突 / 未来证据污染 / 硬性数据错误 | 仅「信息不足」 |
| 必需门控异常 / 产物校验或持久化失败 | 仅「信息不足」或无判断 |
| 必需事件/财务/价格能力不可用，或 PIT 不合格且无合格替代 | 仅「信息不足」 |
| 任一必需专项失败、反证缺失、综合修复上限后仍失败 | 仅「信息不足」 |
| 存在未解决的关键 challenge | 仅「信息不足」 |
| 普通简报无法容纳全部重大限制 | 仅「信息不足」 |
| 必需能力合格、角色完成，仅可选能力缺失 | 四类均可 |
| 必需能力合格且研究链完整，无未处理限制 | 四类均可（**PASS 不自动给「优先核查」**） |

**低优先级与低证据质量是两个独立字段**，不得用「暂缓研究」掩盖系统资料缺失。

## 4. 质量评分表（四项各 0–2，冻结）

对应设计 §13.4。每项独立打分，**不设总分**。

| 项 | 0 分 | 1 分 | 2 分 |
| --- | --- | --- | --- |
| **Q1 问题具体性** | 无明确研究问题，或问题是「持续关注」这类空话 | 有问题但不具体（未指明哪项事实、哪个时间窗口） | 问题指向具体可验证的事实/事件与明确时间范围 |
| **Q2 因果链清楚程度** | 只有结论，无传导路径 | 有传导叙述但环节缺失或跳步 | 催化 → 经营/预期/风险的每一环可追溯，**推断与事实分开标注** |
| **Q3 反证覆盖** | 无反证，或用「未发现反证」代替 | 有反证但未处理/无 disposition | 关键假设的反证被独立提出，**每条有 disposition**，未解决项常显 |

## 5. 性能目标（设计 §13.4，冻结）

> 设计原文：「以下性能数字是**建议优化目标，尚无基线证明能达到**。」

| 指标 | 目标 | 统计口径 |
| --- | --- | --- |
| 输入+输出总 token 中位数 | 较 classic **降低 ≥25%** | 12 案例 × 2 次；**cached 与 uncached 分开**（实测 cache 命中几乎为 0，见 T03 §3.1） |
| 总耗时 p50 | 降低 ≥20% | **不含排队**；**降级 run 分层统计**（§2 警告） |

**基线实测（T03，供 G 对照）**：

| 指标 | classic 基线值 |
| --- | --- |
| LLM 调用数 | 均值 **20.6/run**（区间 14–26） |
| 总 token | 均值 **788,918/run**（p50 ≈ 748k） |
| 墙钟 | min 640s / **p50 2,179s** / max 5,245s |
| 首屏字符 | **p50 8,399**（420 硬上限的 20.0x） |

### 5.1 token 缺失处理（硬规则）

**缺失必须记 `unknown`，绝记 0。** 实测（T03 §3.2）：

- 5 个 failed run 各有 **1 次孤立模型调用**（`model.started` 无配对 `model.completed`）→ token = **`unknown`**；
- 4 个 run 零模型调用（3 cancelled + 1 取数失败）→ token = **`unknown`**；
- **1 个 failed run 烧了 419,932 token** —— 「failed」不等于「没花钱」。

**若某案例的 token 为 `unknown`，该案例**不计入** token 统计的分子或分母，并单列 `n_unknown`。**不得用 0 参与平均。**

### 5.2 目标未达成时的处理

若质量/可读性通过但性能目标未达到：**报告原因和差距，保持显式新入口，先不宣称成本优化成功**。默认切换由产品确认该取舍，**工程不得自行降低门槛**。

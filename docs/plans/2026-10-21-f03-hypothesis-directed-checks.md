## 3. 财务字段扩充

已确认字段（Tushare 字段名）：

| 表 | 新增字段 | 用途 |
| --- | --- | --- |
| income | `oper_cost` 营业成本、`sell_exp` 销售费用、`admin_exp` 管理费用、`rd_exp` 研发费用、`fin_exp` 财务费用 | 毛利、费用率、江淮式费用前提 |
| balancesheet | `accounts_receiv` 应收账款、`accounts_receiv_bill` 应收票据及应收账款、`inventories` 存货、`acct_payable` 应付账款、`accounts_pay` 应付票据及应付账款 | 营运资金、宁德式利润与现金背离 |
| cashflow | `c_pay_acq_const_fiolta` 购建长期资产支付的现金 | 资本开支、自由现金流 |

- **单一注册表**：表 → 字段 → 中文标签 → Sina 代码只在一处定义，采集、内容筛选、数值目录、核查 schema 四处统一读取，消除四份白名单漂移。
- **Sina 代码已实测**（2026-10-21，江淮 2026-06-30 合并期末 CNY，3 次请求）：原有 6 个代码均与现映射一致；新字段代码为
  `BIZCOST`→`oper_cost`、`SALESEXPE`→`sell_exp`、`MANAEXPE`→`admin_exp`、`DEVEEXPE`→`rd_exp`、`FINEXPE`→`fin_exp`、
  `ACCORECE`→`accounts_receiv`、`INVE`→`inventories`、`ACCOPAYA`→`acct_payable`、`ACQUASSETCASH`→`c_pay_acq_const_fiolta`。
  另加两个含票据合计项（用户 2026-10-21 确认）：`NOTESACCORECE`→`accounts_receiv_bill`（应收票据及应收账款）、
  `NOTESACCOPAYA`→`accounts_pay`（应付票据及应付账款）。江淮单项应付 94.9 亿、含票据合计 215.8 亿，
  只取单项会漏掉现金流桥中的应付票据。字段名采用 Tushare 官方名（已核对 tushare.pro balancesheet 文档）。
- **存放方式（用户 2026-10-21 选 A）**：原有 `sina.financial_statements` / `tushare.financial_statements` 证据保持 6 个字段、8 期，
  内容与哈希不变；11 个新字段按表另存为 `sina.financial_detail` / `tushare.financial_detail`，每表一条证据，约 1,500 字符，
  不超过 `SourceContentV1.text` 的 4,000 字符上限。固定检查（`financial_baseline`、`cashflow_comparison`）、
  供应商交叉核对和估值只读原有来源；核查工具、事实与数值目录同时读取明细来源。同期比较仍要求两期来自同一条证据。
- **版本化**：新增 `financial-detail-fields-v1`，写入 native identity。旧运行恢复和重放不采集明细；
  新运行多出明细证据和对应事实，原有财务证据的哈希不变。
- **派生量**：毛利率、费用率等派生量只能由代码按版本化公式计算，不交给模型算。本轮只提供原始字段，派生公式目录单独确认。
- **成本风险**：字段增多会加大内容长度、F02 观察目录和 prompt tokens。需要测量，并作为 F04 的输入。

## 4. 分类契约

挑战 schema 升级为 V3。material / critical 挑战必须填写 `verifiability`：

| 类别 | 含义 | 代码校验 |
| --- | --- | --- |
| `computable_now` | 已保存数据可以当场计算 | 必须带可执行的 `check`，字段、期间、来源须通过现有校验；任务校验规则见第 10 节 |
| `computable_unsupported` | 概念可算，但当前字段、工具或公式输入域不支持 | `required_inputs` 与能力缺口理由必填；已有字段和适用的已支持运算不能被标为能力缺口，详见第 10 节 |
| `needs_source` | 需要补充合格来源、数据，或模型提出资料需求而代码无法判定其可用性 | `required_inputs` 必填；不得把同期间、同口径、可用的保存输入标成缺失，未知可用性须单列 |
| `future_observation` | 要等未来披露 | `observation_date` 必须晚于分析日 |
| `not_testable` | 没有可观察的反证 | 必须写明理由代码 |

- 缺少分类或分类不一致时，走现有的一次修复 → 单条隔离，不新增模型调用额度。
- 任务去向写入记录：已生成 / 已执行 / 执行失败（沿用 `VerificationToolResultV1.reason`）/ 未生成（原因就是分类本身）。
- 回应仍沿用 maintained / revised / withdrawn / unanswerable。核查结果不自动关闭风险，裁决须说明结果为何改变或不改变判断。
- 旧记录没有这些字段，Reader 显示“未知”，不补造执行结论。
- 分类校验只证明结构、保存数据及工具能力自洽，不证明自然语言分类或经济解释正确。

## 5. 链路与计量

挑战 → 分类 → 任务 → 执行结果 → 专项回应 → 综合裁决，ID、作用域和保存证据全程一致。
benchmark 新增确定性计数：分类覆盖率、任务生成率、实际执行率、成功结果率、判断变化。
任务生成率的分母取自夹具中预先标注的“可算”集合，不取决于模型是否生成了 `check`；分母为 0 时记“不适用”。

## 10. A：挑战独立核查命题的实施设计

本节记录本次接力中用户选择 A、独立规格复核后再次确认的设计；实现与限制见第 6 节及独立验收记录。
目标是让重要挑战的核查去向可审计，而不是为了提高核查数量，把未来条件改造成当前可算条件。

### 10.1 命题与原假设的边界

- 挑战 V3 仍指向一个既有 `hypothesis_id`。新增核查命题以挑战的 `proposed_test` 为人类可读文本，
  `check` 为结构化计算定义；二者一起进入挑战身份与保存绑定。
- `condition_id` 可引用原假设的条件作为背景，但不得据此覆盖原条件的文本、角色、来源或时点。
  V3 的任务来自挑战自己的 `check`，不再从所选原条件暗中继承计算式。
- 独立命题只使用冻结 V0 中合格的事实、来源和指标，可以使用原假设未引用的保存事实。
  挑战显式选择新增的 `supporting_fact_ids`；代码校验它们属于 V0 的事实，且所有计算输入均由这些事实的
  证据支持。原假设原有的引用边界不变，不能倒填这些事实使原假设看起来已有支持。
- 挑战解释可引用原假设的事实与本挑战新增事实；回应只能获得该专项原有事实、分配挑战的新增事实及其
  核查结果。不得因此读取其它专项的无关草稿。数值和 F02 观察收据采用同一边界。
- 新 `check` 的 operands、metric 与 predicate 都必须有完整结构化数值绑定；predicate 的计划绑定对应
  本挑战的 `proposed_test`。不能仅扩充可引用事实，却让新增计算输入绕过数值收据。
- 示例：“后续财报出现经营改善”仍是原假设的未来条件；“已保存同期销售费用是否增加”可以成为独立命题。
  费用增加即使被计算确认，也不能直接证明其导致亏损或抵消规模收益。

### 10.2 分类所需输入与校验

`required_inputs` 使用类型化描述，区分财务字段（表、字段、期次与所需口径）、保存指标及补充资料。
财务字段名在需求描述中可超出白名单，用于准确登记能力缺口；可执行 `check` 仍必须通过既有白名单。
补充资料描述属于待研究需求，不能作为已有事实引用。

| 分类 | 进一步约束 |
| --- | --- |
| `computable_now` | 必须有 `check` 和绑定事实；字段、期次、披露资格、单位和比较口径可由保存输入确认。禁止同时填写未来观察或能力缺口理由。非正增长基数等已知不可计算输入不能被预检称为可算；两期财务比较须来自同一条 evidence ID，同 source family 不足以通过 |
| `computable_unsupported` | 无可执行 `check`；理由区分字段不受支持、指标不受支持、运算不受支持和 `input_domain_unsupported`。已支持字段有合格保存输入时，不得称为“字段不受支持”；但已有原始字段并不意味着跨字段比率等尚未提供的公式已受支持。零或负同比基数明确归 `input_domain_unsupported`：当前 growth 公式仅定义在正基数上，不偷偷替换为除以绝对值等新公式；输入及不适用域可由代码检查，去向为该分类下未生成任务 |
| `needs_source` | 无可执行 `check`；至少一项需求满足以下之一：代码确认在相同期次与口径下缺失或不合格，或模型提出的自然语言资料需求无法由代码判定可用性。后者保存 `availability_unknown` 与模型提出属性，不计入“代码已确认缺失”数量。不同期次、不同口径、截断正文或不合格披露不算已具备所需输入；已由代码确认具备的输入不得记作未知或缺失 |
| `future_observation` | 无可执行 `check`；观察日期必须晚于分析日。不得把未来日期作为当前执行结果；日期仍受数值计划绑定约束 |
| `not_testable` | 无可执行 `check`；理由限定为没有可观察反证或测量定义不明确。保留模型分类属性，不声称代码已证明不可检验 |

只有 material / critical 强制分类并进入覆盖率分母。minor 可不分类；未分类时不为它虚构新核查任务。
同一挑战最多一个任务，总计仍最多三个任务、一个补充轮次；不增加外部检索、派生公式或模型额度。

### 10.3 版本与保存归属

- 新增冻结策略 `hypothesis-directed-checks-v1`，只用于新建 V7 运行；旧运行缺少该策略时继续选择旧挑战、
  原条件任务和原校验路径。恢复时不静默升级，不重新采集、不补写历史分类。
- `_native_stage.py` 拥有 V3 模型提议；分类与需求的中立模型由 `agents/schemas/` 拥有，
  `research/` 的纯函数负责输入可用性、作用域校验及任务装配。
- 引入 `verification-plan-v2` 和挑战命题任务类型，绑定挑战、目标假设、独立命题及 `check`。
  V1 继续要求原假设条件文本一致；V2 不冒用 `necessary` / `invalidation` 的原条件角色。
- 正式研究记录保存提议中通过校验的分类、需求、独立命题与 `check`。每个已分类挑战另有代码拥有的任务去向，
  包含未生成原因，或任务 ID、plan 哈希及执行状态；执行失败保留工具原因。
- 新结果使用明确的挑战命题作用域。计算结果保存数值、`predicate_met` 和实际执行时间；命题满足/不满足与
  经济假设支持/反驳分别解释。原 `supports` / `contradicts` 状态如被复用，仅代表绑定命题，不能自动产生
  风险关闭或专项 disposition。Reader 与导出必须同时显示命题和作用域。
- 历史记录新增字段缺省时保持既有序列化与哈希；未知策略、错误快照、越界引用、改变命题/任务绑定或被篡改的
  去向在恢复和发布时拒绝。只读 Reader 与导出均不执行核查。

### 10.4 修复、隔离与执行状态

- 先逐挑战校验，保留通过条目的原始索引与收据。分类、引用或数值错误使用现有一次结构修复机会；
  修复可用额度仍受全局预算限制，不保证有额外额度。
- 修复整体有效时采用修复产物并重新完整校验；否则回退到首次提议中通过校验的条目。
  被拒条目只保存索引和封闭原因码，不把未验证正文作为正式挑战、核查事实或零挑战成功。
  全部条目失败时明确记录挑战阶段不可用；有效的零挑战与全部拒绝必须可区分。
- 数值和 F02 收据、ID 生成、缓存、恢复、阶段 Reader 与最终发布必须使用同一组已接受索引，
  不得只过滤正文而遗留旧路径收据。
- 去向区分：未生成（分类或拒绝原因）、已生成但取消、预算拒绝、派发状态未知、已执行但无法计算、
  已执行并得出谓词结果。工具异常沿用 `tool_failed`；未执行项没有执行时间或虚构结果。
- 保存结果优先于后来的取消；未知派发不自动重试；缓存/恢复复用同一任务与结果，不重复执行。
  底层预算、原子保存和发布屏障沿用现有执行器。

### 10.5 消费者与计量

- 专项回应和综合上下文携带分类、独立命题与代码拥有的去向。维持、修正、撤回、无法回答继续沿用现有规则；
  综合须解释结果为何影响或不影响判断，不能因谓词为真自动关闭经济问题。
- Reader、相关依据、阶段输出和 Markdown 展示分类、所需输入、命题、执行状态及限制。
  老记录缺分类显示“未知”；固定检查结果与本链路独立展示、独立计数。
- benchmark 区分两个口径：运行记录的“已接纳条目分类完整率”为合法分类的重要挑战数 /
  全部已保存重要挑战数，只用于检查契约完整性；不能据此声称覆盖了所有应提出的挑战。
  离线“分类覆盖率”使用冻结人工标注的重要挑战集合为分母，分子为其中被正确识别、分类并接纳的挑战数。
  重复匹配不增加分子；遗漏、隔离、修复后删除和全拒均留在该分母中。离线 fixture 使用预先冻结的 case/target
  映射对齐，真实模型的语义匹配需人工标注，不能仅凭同一 hypothesis_id 推定匹配。无此标注的真实记录
  分类覆盖率为 null；拒绝条目数和全拒阶段另报。历史未分类不是零执行错误。
- 任务生成率只在有冻结人工标注的离线样本集合上计算，分母为其中预先标注的可算重要挑战数；
  分子为该集合中生成正确绑定任务的挑战数，错误命题/来源/期间/计算式不能计为成功。
  历史真实记录缺少此标注时为 null，不根据模型 `check` 或分类倒推分母。
- 实际执行率为有执行时间的任务数 / 已生成任务数；成功结果率为获得有效谓词结果的任务数 /
  已执行任务数。数据不合格、工具失败单列；分母为零记 null 并标注不适用。
- 判断变化分别计数 maintained / revised / withdrawn / unanswerable，不将变化比例等同于判断质量提升，
  不把局部回应变化算作固定证据对照下的总体倾向变化。

### 10.6 实施与验收切片

1. **契约与纯校验**：V3 分类、类型化需求、命题任务 V2、保存记录及代码校验；测试五类、自洽性错误、
   已有字段假缺失、已有字段但运算不受支持、零/负增长基数的输入域缺口、自然语言资料可用性未知、
   同 source family 但不同 evidence ID 的比较拒绝、未来日期、越界事实/来源、原假设不可改写。
2. **运行链路与恢复**：策略身份、挑战提示、一次修复及隔离、数值/F02 收据、任务执行与去向、回应和综合、
   发布校验；测试取消、预算拒绝、未知派发、工具失败、保存结果后取消、篡改绑定与旧版本恢复。
3. **读取与导出**：Python 投影先行，同步 TypeScript、Reader 和 Markdown；验证历史未知、新命题作用域、
   相关依据及阶段输出，执行 typecheck / Vitest / build 与 Reader E2E。
4. **离线验收与计量**：江淮两条真实挑战只读提取并保存记录/证据哈希，人工重标注不能当作模型服从度；
   其中财务明细缺失时必须保留缺失结论，不能把后来抓取的数据悄悄塞回历史证据。
   合成夹具覆盖新字段可算情形与每种分类/执行状态，给出确定性 benchmark 计数；加入隔离、遗漏、修复后
   删除、重复匹配及错误任务的计数反例，证明冻结分母与正确任务分子不被结果反向改写。

本设计在 10-21 验收时仍受第 8 节已知失败约束；10-22 用户另行授权修复后，状态见上面的接力更新。
两次分层验收都不能替代干净全量基线。本设计不授权真实模型运行、用户服务重启、Git 发布或用户数据迁移/清理。

# 证据驱动多 Agent 研究架构优化方案（V8 提案）

Status: Proposed

**Do not use this document as evidence of current implementation behavior.**

- 日期：2026-10-17；基线代码：`main@234304b`（V7：`evidence-production-v7` / `native-research-kernel-v6`）。
- 实测：Web 工作台 + ChatGPT 订阅 `gpt-6-luna`，宁德时代 300750.SZ，另对本地已保存运行做统计。
- 约束（已与用户确认）：无需实时分析；可忽略历史数据与历史版本兼容；模型预算不设硬限但不浪费；范围覆盖采集、推理、发布、UI 与 Reader。

## 0. 结论摘要

1. 多数“证据不足”不是数据源没数据，而是证据加工层没把已获取的数据变成可用事实：财务字段被收窄到 6 个、PDF 表格解析失败时检查直接判不可用、派生指标几乎不存在、公告标题占了一半事实。
2. 推理链路弱有三个结构性原因：专项按“数据来源”切分而不是按“研究问题”切分；Prompt 只有一句方法论；质疑不能触发任何可执行检验或补证，挑战→回应只产生更多免责措辞。
3. **最直接的问题：V7 综合阶段在本地全部 8 次运行中都失败，修复 0 次成功，代码核查 0 次执行。**用户看到的“证据不足”，大部分其实是“综合失败后的降级外壳”。综合是一次性大 JSON，任一引用错误整份报告作废，且每次运行 16–60% 的 token 花在这里。
4. 判断层用二元门槛（`unresolved` / `no_favorable` / `insufficient_evidence`）表达不确定性，挑战裁决被 schema 固定为 `unresolved`，系统的最优策略变成“少说、多免责”。
5. 方向：从“冻结证据 → 一次性流水线 + 层层禁止”升级为“问题驱动的证据图 + 有界补证闭环 + 代码计算的校准置信度”。代码继续拥有事实、数字、引用、时点和发布；模型负责提出、检验和权衡判断。
6. 路线分 6 个阶段：Phase 0 先修综合失败并建评测基线（单这一项就能让现有数据产出有评级的报告），再改数据模型和推理结构。每阶段都有可量化验收。

## 1. 第一性原理：系统到底在优化什么

给定截止时点 `t` 和有限证据集 `E`，系统输出判断 `J = (立场, 置信度, 理由, 反证, 改变判断的条件)`，同时满足：

| 目标 | 性质 | 当前状态 |
| --- | --- | --- |
| A. 可追溯：每个断言能回到 `E` 中的来源与计算 | 硬约束 | 做得很好，甚至过度 |
| B. 校准：置信度与证据充分度相匹配 | 软目标 | 用二元门槛代替，缺失 |
| C. 信息量：在能回答的问题上给出明确回答 | 软目标 | 被 A 的实现方式压制 |
| D. 效率：token 花在推理上，不花在搬运上 | 软目标 | 输入/输出约 90:1 |

当前设计把 B、C 当作 A 的副产品：凡不能被证明的就禁止。由此推出五条设计原则：

1. **事实、数字、引用、时点归代码**（保留）。但“能否下判断”不应是二元门，而是证据充分度的函数。
2. **证据充分性相对于问题，而不是相对于数据源。**“是否有 PDF 数值行”不是研究问题，“现金转化是否健康”才是。需要显式的问题树。
3. **推理质量 = 假设的信息量 × 被检验的强度。**检验必须能由代码执行，否则质疑会退化为“需进一步核实”。
4. **有限数据下正确运行 = 知道哪些问题能答、哪些不能、缺什么会改变答案。**这是 value of information，而不是一律降级。
5. **上下文只给与当前问题相关的子图。**把 1 MB 记录反复喂给每个阶段既贵又稀释注意力。

## 3. 根因：逐层定位

| 层 | 现状 | 问题 | 代码位置 |
| --- | --- | --- | --- |
| 采集 | native 收集器只用身份、三表、公告/PDF、行情、估值、预测、同行 | 仓库里已有的 a-stock-data 适配器（回购进度、质押、解禁、股东户数、龙虎榜、北向、融资融券、机构调研、业绩预告、研报、板块/行业）未接入 native | `dataflows/minimum_sources.py` vs `dataflows/a_share_events.py`、`china_specialty_em.py`、`china_capital_flow.py` |
| 资格 | 资格判定基本是二元：合格或 unavailable | 一个格式问题就丢掉整类证据；没有质量分级，也没有跨源互证加分 | `research/minimum_evidence.py:qualify_payload`、`native_record.py:_financial_content` |
| 加工 | 事实 = 原始字段的文字转述 | 没有派生事实层：增速、利润率、ROE 分解、现金转化率、营运资金周转、前瞻 PE、PEG、相对收益都要模型自己算，而数值政策又禁止模型写数字 | `research/native_record.py`、`numeric_catalog.py` |
| 视图 | `fact_views` 按 source_name 把事实分给三个专项 | 专项看到的是“某类数据”，不是“某个问题的证据”；估值没有专属角色；市场专项只剩价格统计 | `research/native_policy.py:fact_views` |
| 方法 | 每个专项一句英文指令 | `tradingagents/skills/library/` 的方法论（财报分析、估值、事件检测、市场状态）只接在 classic 角色上 | `execution/native_model.py:STAGE_INSTRUCTIONS`、`skills/registry.py:ROLE_SKILL_NAMES` |
| 检验 | 条件核查要求模型构造 `FinancialConditionV1/MetricConditionV1` | 构造难度高，模型普遍选择 `check: null`；可检验的只有 6 个字段 | `agents/schemas/_verification_plan.py` |
| 对抗 | 一个 critic，≤3 条挑战，一轮回应 | 挑战不能请求证据或计算；回应不能获得新事实；没有“过度保守”方向的挑战 | `graph/native_research.py`、`research/unified_dialogue.py` |
| 判断 | 维度 `conditional/unresolved` + `stance_ceiling` | 不确定性只有门槛，没有程度；所有挑战强制保留 `unresolved` | `research/unified_assessment.py`、`native_policy.py:dimension_policy` |
| 综合 | 单次 `SynthesisProposalV3` 大 JSON | 结构耦合太强，一处引用错误整体失败；修复只有一次 | `graph/native_research.py:_call("synthesis")`、`execution/native_model.py` |
| 上下文 | critic/synthesis 收到整份记录 | 输入 token 巨大，注意力被 87 条公告标题和免责字段稀释 | `graph/native_research.py:critic_context / synthesis_context` |
| 版本 | V1–V7 七套 collector/kernel/prompt，`native_identity` 有 7 个布尔开关 | 每加一项改进就要再加一个 identity 标记，改动成本越来越高 | `execution/native_runner.py:native_identity / validate_native_resume` |

一句话：**当前系统的约束层很完整，但约束作用在了“表达”上，没有作用在“获取和检验”上。**

## 4. 目标架构（V8）

```text
                ┌──────────────────────────── code-owned ────────────────────────────┐
 Source         │ Capability registry → Qualification(分级) → Fact compiler(派生指标)  │
 adapters  ───► │        │                                       │                    │
                │        ▼                                       ▼                    │
                │                  Evidence Graph（单一数据模型）                       │
                │   Source ─derives→ Fact ─derives→ Metric ─answers→ Question         │
                │   Hypothesis ─supports/contradicts→ Question   Check ─tests→ Hypo   │
                └────────▲───────────────────┬───────────────────────▲──────────────┘
                         │ bounded evidence  │ question-scoped packs │ typed nodes
                         │ requests          ▼                       │ (validated)
                ┌────────┴──────────────── model-owned ──────────────┴──────────────┐
                │ Agenda planner → Lens specialists ×4 → Adversarial loop (≤2 轮)     │
                │                                     → Sectioned synthesis           │
                └────────────────────────────────────────────────────────────────────┘
                         │
                         ▼
          Calibrated judgement（代码计算充分度/置信带）→ Publication → Reader 2.0
```

核心变化：模型不再“读一大段记录写一大段 JSON”，而是在一张代码维护的证据图上**提出类型化节点**（假设、检验请求、挑战、回应、裁决），每个节点单独校验、单独失败、单独修复。

### 4.1 证据层：先把已有数据用足

目标：同样的数据源，让可用事实数量和质量翻倍；有限数据下仍能得到核心问题的答案。

1. **能力注册表（Capability registry）**。每项能力声明：所需字段、候选供应商顺序、PIT 规则、质量等级、是否核心。把 classic 已有的 a-stock-data 适配器以“可选能力”接入 native：回购进度、股权质押、限售解禁、股东户数、业绩预告/快报、机构调研、研报列表、融资融券、北向持股、龙虎榜、所属行业/概念及行业指数。
2. **财务字段扩展**。三表白名单从 6 个扩到约 40 个核心科目（营业成本、三费、研发、毛利、应收/票据、存货、合同负债、预付、固定资产、在建工程、货币资金、短/长期借款、应付债券、资本开支、分红、少数股东损益等）。Sina 与 Tushare 同字段互证。
3. **结构化优先，PDF 补充**。`operating_disclosures` / `cash_conversion` 在 PDF 数值行缺失时，允许用合格的结构化三表回答同一子问题，并把“与官方原表互证”作为加分而不是前提。PDF 只用于分部收入、产能、出货等结构化源没有的数据。当前依赖是 `pypdf`（纯文本抽取）；若改用带表格抽取的库（如 pdfplumber），属于新增依赖，Phase 2 实施前单独确认并固定版本。
4. **质量分级代替二元资格**。

   | 等级 | 含义 | 例 |
   | --- | --- | --- |
   | A | 官方原文且数值解析成功，或两家独立供应商一致 | 年报表格、Sina=Tushare |
   | B | 单一可信供应商结构化字段 | Sina 三表、腾讯估值快照 |
   | C | 选取样本、机构预测、解析置信度低的摘录 | 同行候选、EPS 预测 |
   | D | 线索：仅标题、无正文 | 公告标题 |

   只有身份不符、时点越界、内容篡改才拒绝；其他问题降级并记录原因。
5. **基准与行业**。上证/深证/创业板/沪深300 及申万一级行业指数日线进入行情证据，市场专项才能计算相对收益、beta、行业相对估值。

### 4.2 事实编译器（Fact compiler）

代码把原始字段编译成派生事实，模型直接引用，不再自己算：

| 类别 | 派生指标 |
| --- | --- |
| 增长 | 收入/归母净利/扣非/经营现金流同比、环比、TTM、近 8 季趋势斜率 |
| 盈利 | 毛利率、净利率、期间费用率、研发费用率及其同比变化 |
| 回报 | ROE、杜邦三因子（净利率 × 周转 × 杠杆）、ROIC 近似 |
| 现金 | CFO/净利润、自由现金流、资本开支强度、应收/存货/合同负债变化对 CFO 的贡献 |
| 资产负债 | 资产负债率、有息负债/权益、现金/短债、流动比率 |
| 估值 | PE/PB 分位、前瞻 PE（各机构 EPS）、PEG、相对行业中位数折溢价、隐含增长 |
| 市场 | 相对基准收益（20/60/250 日）、beta、波动率分位、换手、资金/筹码变化 |
| 事件 | 公告分类（业绩/资本运作/治理/经营/例行）、去重、重要性分级；例行公告折叠 |

每个派生事实带 `formula_id`、输入节点、计算版本和单位，进入现有数值目录，模型通过 `{{num:...}}` 引用。这样数值政策从“禁止模型写数字”变成“模型可以引用丰富的、代码算好的数字”。

### 4.3 证据图（Evidence Graph）作为唯一数据模型

用一张有类型的图替代当前分散的 `claims / hypotheses / challenges / verifications / dialogue / challenge_bindings / numeric_attribution`：

- 节点：`Source`、`Fact`、`Metric`、`Question`、`Hypothesis`、`CheckSpec`、`CheckResult`、`Challenge`、`Reply`、`Judgement`。
- 边：`derives_from`、`answers`、`supports`、`contradicts`、`tests`、`targets`、`revises`、`withdraws`。
- 一套图校验规则代替现在十几个分散的绑定校验（引用存在、角色作用域、修订/撤回不能支撑、仅 `CheckResult` 能写“已执行”等）。
- 置信传播：每条支撑链的强度 = 事实等级 × 来源独立性 × 检验结果。Reader 可以直接标出“这个结论最弱的一环”。
- `numeric_attribution` 改为按节点保存哈希和公式 ID，不再重复保存整段收据，目标把记录体积降到当前的 1/4 以下。

### 4.4 研究议程（Question tree）

代码维护公司研究问题模板，每个问题声明所需证据与最低充分度：

| 问题 | 核心证据 | 最低要求 |
| --- | --- | --- |
| Q1 商业模式与竞争位置 | 主营、分部、行业 | 主营业务 + 一项定量经营数据 |
| Q2 增长质量与可持续性 | 收入/利润 8 季、分部、预告 | 两期同比 |
| Q3 盈利能力趋势 | 毛利率、费用率、ROE 分解 | 两期利润率 |
| Q4 现金转化 | CFO/净利、营运资金、资本开支 | 两期 CFO 与净利 |
| Q5 资产负债与风险 | 负债结构、现金/短债、质押 | 最新资产负债表 |
| Q6 资本配置与治理 | 分红、回购、减持/增持、质押、解禁 | 公告分类结果 |
| Q7 估值与预期 | PE/PB 分位、同行、前瞻 PE、PEG | 一个合格估值锚点 |
| Q8 事件与催化 | 重要公告正文、业绩预告、调研 | 可选 |
| Q9 市场与资金 | 相对收益、资金、筹码 | 可选 |

一个有界的 planner 调用可以追加最多 3 个公司特定问题（如“储能业务占比提升对毛利率的影响”），但不能删除模板问题。问题是充分度打分、上下文切片和 Reader 导航的共同单位。

### 4.5 按“研究视角”而不是按“数据来源”组织专项

| 新专项 | 负责问题 | 证据包 |
| --- | --- | --- |
| 经营与财务质量 | Q1–Q5 | 三表派生指标、分部、PDF 摘录、预告 |
| 估值与预期（新增） | Q7 | 估值快照/历史、同行、预测、Q2/Q3 的增长与利润率 |
| 事件与治理 | Q6、Q8 | 分类后的公告正文、回购/质押/解禁、调研 |
| 市场与资金 | Q9 | 相对收益、beta、资金、筹码、行业指数 |

- 证据包按问题跨来源切片，专项之间的草稿仍然隔离（保留独立性）。
- 每个专项注入 1–2 张方法卡，来自已有 `skills/library`，并改写为 native 版本：经营用 `financial-statement-analyzer`，估值用 `bayesian-intrinsic-growth-valuation` / `tam-adj-peg`，事件用 `event-driven-detector`，市场用 `market-regime-and-health`。方法卡仍由代码映射，不能新增工具。
- 每个专项输出：对每个负责问题的回答、类型化假设、自评充分度、以及“哪项缺失证据最可能改变我的判断”。

### 4.6 检验编译器与有界补证闭环

**检验编译器。**模型不再构造数值绑定 JSON，而是从封闭菜单里选检验模板，代码负责绑定节点和执行：

```text
metric_compare(metric_id, op, threshold)         例：CFO/净利 ≥ 0.8
trend(metric_id, periods, direction)             例：毛利率近 4 季不下降
peer_rank(metric_id, percentile_op, threshold)   例：PE 低于同行中位数
consistency(source_a, source_b, field)           例：Sina 与 Tushare 归母净利一致
event_exists(category, window)                   例：近 90 天有无减持/质押公告
```

代码把模板编译成现有 `VerificationPlanV1` 的扩展版本执行。每条假设至少带一个可执行检验；无可用模板时必须说明原因，这本身计入充分度。

**补证请求（Evidence request）。**专项和 critic 可以发出类型化补证请求，代码从封闭能力菜单中执行：

- 只能请求注册表中的能力，受同一 PIT、时点和预算规则约束；
- 每个运行最多 1 轮补证、每轮最多 N 个请求（建议 N=6），请求合并去重后并行执行；
- 结果经资格判定、事实编译后作为新节点进入图，形成 `snapshot v1`（保留 v0 不变，lineage 可追溯）；
- 只有被补证影响的问题和假设进入下一步，其他不重跑。

这就是“推理 → 发现缺口 → 补证 → 再推理”的闭环，但工具面仍是代码拥有、可审计的。

### 4.7 对抗深化：自适应多轮 + 双向挑战

1. **挑战类型化**：`counter_evidence`（指向已有相反事实）、`alternative_explanation`（必须附一个能区分两种解释的检验）、`missing_evidence`（必须附补证请求）、`logic_gap`（指出推理跳跃）。泛泛的“需进一步核实”不再是合法挑战。
2. **双向**：critic 同时检查“过度自信”和“过度保守”。例如“估值处于 2% 分位且低于同行一半，专项却没有任何估值判断”应是一条合法挑战。这一条直接对应当前系统的系统性偏差。
3. **Pre-mortem**：critic 的固定任务之一是“假设 12 个月后这个判断被证明错了，最可能的原因是什么”。
4. **自适应轮次**：第 1 轮挑战 → 执行检验 / 补证 → 专项回应（可以用新事实）→ 只对仍有争议、且严重度 ≥ material 的项进入第 2 轮。上限 2 轮；若一轮没有产生新事实或新检验结果，提前停止。
5. **上下文**：critic 只看假设、其支撑子图、检验结果和问题树摘要，不再看完整记录。

关于“常驻反方 Agent 审批每条假设”：不建议做成审批门。审批门会把系统进一步推向保守，并把延迟翻倍。上面的“双向 critic + pre-mortem + 多轮”承担了反方律师的作用，但不阻塞流程。

### 4.8 校准判断：充分度代替二元门槛

**问题充分度**（代码计算，0–1）：

```text
sufficiency(Q) = coverage(Q) × quality(Q) × consistency(Q) × test_factor(Q)
  coverage    = 已满足的必需证据 / 该问题的必需证据
  quality     = 支撑事实等级的加权均值（A=1.0, B=0.8, C=0.5, D=0.2）
  consistency = 1 − 未解决矛盾边的惩罚
  test_factor = 检验支持↑ / 检验反驳↓ / 未检验 = 中性
```

**维度置信带**：由所属问题的充分度聚合为 `high / medium / low / insufficient`。

**立场规则**（替代 `stance_ceiling`；**已确认（2026-10-17）**：除非核心财务完全缺失，否则必须给出带置信度的立场，并标注哪些部分数据欠缺）：

| 条件 | 允许的立场 |
| --- | --- |
| Q2–Q4 全部 `insufficient`（没有任何可用财务） | 只能 `insufficient_evidence` |
| 有未解决的 critical 挑战 | 禁止 `favorable` |
| 估值维度 `low` 或 `insufficient` | 禁止 `favorable` 的 high 置信 |
| 其余 | 任意立场，置信度 = 相关维度置信带的下限 |

**数据欠缺标注**：立场旁固定显示“部分数据欠缺”清单，列出置信带为 `low / insufficient` 的问题及缺失的具体证据（例如“Q4 现金转化：缺营运资金明细，置信度低”）。标注由代码根据充分度生成，模型不能删除或弱化。

**输出 value of information**：列出“补齐后最可能改变立场的 3 项缺失证据”，按影响排序。这就是“有限数据下正确运行”的具体形态：给出判断、标明置信、说清楚缺什么。

**挑战裁决**：挑战附带的可检验命题由代码检验结果标为 `supported / refuted / open`。这只针对该命题本身；挑战背后的经济判断仍由综合给出理由并标注置信度，不被代码结果自动关闭。也就是说，不再强制所有挑战永远 `unresolved`，但“检验通过”不等于“经济问题已解决”。

**参数**：A–D 权重、`consistency` 惩罚、`test_factor` 系数和置信带阈值（初始建议 high ≥ 0.75、medium ≥ 0.5、low ≥ 0.25）都是代码常量，入库版本化。Phase 5 用 3 家基准的结果做一次人工校对后再定稿，之后改动需要说明理由。

### 4.9 分段综合

把单次大 JSON 拆成代码骨架 + 模型填空：

1. 代码先生成骨架：维度顺序、每个维度可引用的节点 ID、置信带、待裁决挑战列表、立场允许集合。
2. 模型分段填写：(a) 每维度判断；(b) 每条挑战裁决；(c) 总体立场与理由；(d) 改变判断的条件。可以一次调用输出全部分段，但**按分段校验**。
3. 某一分段失败只修复该分段；修复仍失败则该分段降级为“未完成”，其余分段保留。不再出现“综合整体作废 → 专项汇总”。
4. 引用字段用 JSON Schema `enum` 约束到骨架提供的 ID。若供应商支持 structured outputs（OpenAI Responses `text.format=json_schema`，需要对 ChatGPT 订阅端点实测），可直接消除引用类错误；不支持时保留现有 alias + 校验 + 修复路径。

**已确认并实现于 Phase 0（2026-10-18）**：总体判断或任一 `critical` 挑战的裁决在既有一次修复后仍失败时，保留有效分段但暂不评级，明确显示“综合未完成”；不将执行/校验失败写成“财务证据不足”。其他失败分段保留有效总体判断并标注部分交付。当前仍使用 V7 的证据门槛和 8 主调用／12 总尝试，不提前采用 Phase 5 的判断规则。实现与离线验证见[分段综合记录](../reviews/2026-10-18-v8-phase0-sectioned-synthesis.md)。

### 4.10 上下文与成本

- 每阶段只收到与其问题相关的证据包；critic/synthesis 收到问题树摘要和相关子图，而不是全部记录。目标：单次运行输入 token 降到当前的 30–40%。
- 固定前缀（系统指令、方法卡、schema）放在前、动态内容放在后，便于供应商的前缀缓存。
- 公告标题类 D 级事实默认折叠，只在事件专项的证据包中出现分类摘要。
- 模型：**已确认（2026-10-17）全部阶段使用同一个模型**，不做快/深分工。表单的“专项与挑战模型 / 综合模型”两个选择可在 Phase 5 合并为一个。

### 4.10a 调用编排与预算

V7 是 8 次主调用 + 12 次总尝试。V8 的阶段更多，必须先定上限，避免“先进”变成“浪费”：

| 阶段 | 主调用 | 说明 |
| --- | --- | --- |
| Planner | 1 | 只追加公司特定问题；失败则只用模板问题，不阻断 |
| 四个视角专项 | 4 | 并发上限 2 |
| Critic 第 1 轮 | 1 | |
| 补证 | 0 | 代码执行，计入数据预算，不计模型预算 |
| 回应第 1 轮 | ≤ 4 | 只调用被挑战的专项，多个挑战合并为一次调用 |

## 7. 不变量（任何阶段都不放松）

- 事实、数字、引用、时点、资格判定、检验执行和发布授权归代码；模型不能创造事实或写“已执行”的检验。
- 证据快照冻结且有 lineage；补证产生新快照，不改写旧快照。
- 不生成订单、目标仓位或交易指令；Web 只绑定 `127.0.0.1`；凭据不进入运行记录。
- 来源内容是不可信数据，不执行其中的指令。
- 未知调度不重放；取消与发布授权仍在同一生命周期锁下仲裁。

# Insight 优先的多 Agent 研究：迭代待办草案

日期：2026-10-28。Status: Approved direction; protocol design in progress。

本文方向已获用户确认，具体协议样例正在细化；不是已实现的行为或逐函数实施方案。
Do not use this document as evidence of current implementation behavior.

当前实现以 [研究契约](../contracts/research-record.md)、[架构](../../ARCHITECTURE.md) 和代码为准。
用户已授权继续推进。真实模型调用、Git 发布和服务生命周期操作仍需遵守原授权边界。

用户随后确认：新流程由综合 Agent 判断依据是否充分；程序只核验引用、数值及有效版本，资料缺口必须明示。缺少旧程序规定的估值锚点不再自动禁止“有利”判断；旧记录保留原规则。

## 1. 目标与职责

目标：多 Agent 产生高质量 Insight，交叉质疑提升判断质量，证据系统让判断可追溯。

| 参与方 | 应负责 | 不应负责 |
| --- | --- | --- |
| 专项 Agent | 观点、相关证据、推理、反证或局限；直接用清楚的语言表达 | 字段路径、计算凭证、机器观察位置、复杂发布规则 |
| 质疑与回应 Agent | 哪个判断可能错误、证据不足在哪里、替代解释；据此维持、修订或撤回观点 | 为凑分类而产生挑战、机械填满风险与测试分类表 |
| 程序 | 来源保存、引用解析、数值与单位计算、版本与状态、局部隔离、最终证据链检查 | 凭引用数量推断观点正确、自动编造评级、代替 Agent 作经济判断 |
| 综合 Agent | 权衡已经保存的 Insight、质疑和回应，形成有依据的总体判断和待验证事项 | 引入没有保存的新事实、把未验证观点当已知事实、逐项机械填裁决表 |

“研究综合”就是最后的研究判断。例如：经营 Agent 认为利润增长改善了业务；质疑 Agent 指出增长可能来自一次性收益；回应修订了原观点。综合 Agent 应解释持续经营改善还剩多少依据、这会怎样影响公司判断，而非简单拼接三段文字。

程序可以证明来源存在、片段可定位、数字计算可复现，不能仅靠 JSON 或引用存在证明来源真实、证据充分或因果推断正确。语义相关性和推断力度由研究、质疑、综合共同审视，并向用户展示局限；不承诺“程序保证一切事实绝对正确”。

## 2. 本次明确调整的验收口径

- 白话解释的全覆盖率不是研究验收指标，也不影响报告、综合结论或评级是否成立。当前实现已经将解释任务与研究完成分离；此前把解释覆盖率混入研究验收的口径需要纠正。
- 优先要求 Agent 原始观点及理由可读。已有额外白话解释可保留为阅读辅助；本计划不擅自删除历史解释或改变自动触发方式。
- 不要求每个 Insight 必须存在有效反证。明确记录“已审阅但未发现有效反证”、未审阅、审阅失败三者的区别；无反证不代表观点被证明。
- 有合格 Insight 就允许部分研究交付；没有合格 Insight 时只交付资料和失败说明，不称为完成分析。无整体判断时不产生默认评级。
- 真实验收分别评估研究内容、证据追溯与故障隔离；不以 HTTP 成功、JSON 合法、任务 completed 或报告文件存在替代。

## 3. 实施路线选择

推荐：为新研究引入独立版本的简化协议，复用数据采集、来源存储、计算能力和执行基础设施；旧记录保留原版本读取与回放。新协议不能最终又强制转换成完整旧 envelope，令已移除的约束重新成为发布门槛。

两种替代路线不作为首选：继续在旧协议上删几项校验，改动较小但难以解除层层耦合；整体重写系统，迁移风险大且会重复已有可靠基础设施。推荐路线需要更新存储和 Reader，但改变集中在研究产物及其消费边界。

已有结构化输出接入、安全诊断和 schema 适配可复用。原 [结构化输出修复计划](2026-10-28-structured-output-and-condition-reference.md) 保留为旧协议修复记录，不追改历史事实；其中条件索引等机制继续服务旧记录，新 Insight 协议不要求模型使用它们。

## 4. 迭代待办

### 1）冻结最小协议与边界样例

- [ ] 以四项内容定义 Agent 的 Insight：观点、证据引用、推理理由、反证或局限。使用浅层固定结构；ID、作者、版本、状态与内部索引由程序补充。
- [ ] 引用只允许使用当前提供的短证据编号；程序映射到已保存来源与片段。事实型句子就近引用，避免只在一整段末尾堆来源而无法判断支持关系。
- [ ] 定义数字接口：已有数值以指标引用表达，由程序展示数值、单位、期间；衍生数字由程序依据明确输入和支持的公式计算。无法支持的计算请求进入待验证，不让模型伪造结果或手写计算证明。
- [ ] 明确最小状态：可用于综合、待验证、已排除。状态和机器核验记录由程序保存；“可用于综合”表示来源与数值链满足要求，不表示观点被证明正确。修订或撤回保留历史版本。
- [ ] 用具体样例审阅协议：有效观点、只有推理但证据不足、错误引用、错单位/期间、无反证、局部损坏。确认后再定具体类名、版本号及实施任务。

交付：一份短协议、输入输出样例和校验归属表。硬校验覆盖可确定的事实，不能把自由研究推理重新编码成庞大规则表。未引用的事实性数字不能直接作为合格事实发布；年份、编号等文本不能被误当作财务计算。

主要代码归属：`tradingagents/agents/schemas/`、`tradingagents/research/native_versions.py`；旧 `_native_stage.py`、`_numeric_stage.py` 是迁移盘点对象，不直接放宽其冻结契约。

### 2）打通“单条 Insight → 保存 → 可追溯展示”

- [ ] 先接入一个专项，完成四项输出的边界校验、证据解析、数值渲染、保存和展示，验证协议能实际降低模型负担。
- [ ] 复用来源、片段和数值 catalog 的能力，将复杂字段路径、绑定和证明放在程序内部。不同公司、日期、单位及口径不能被静默混用。
- [ ] 按 Insight 隔离：一个结构错误、坏引用或数值问题不丢弃同批合格观点；可解析但支撑不足的观点保留为待验证，完全无法解析的条目保留安全诊断。
- [ ] 最多一次针对失败条目的修复，计入已有总预算；不重新生成已接受条目。整体 JSON 无法解析时不能声称已恢复其中观点。
- [ ] 确认链路后复用到经营、事件、市场专项；复用统一 Insight 契约，不为每个 Agent 再造一套复杂协议。

交付：有来源可点击、有数字可复算的研究条目，即使同批有坏条目也可阅读。

主要代码归属：`execution/native_model.py`、`graph/native_research.py`、`research/numeric_catalog.py`、新 Insight 保存与解析模块、`web/reader_stage_projection.py`。参考回归：`tests/web/test_specialist_isolation_publication.py`、数值及 Reader 测试；增加新协议自身的针对性测试，不能只测试旧 envelope。

### 3）将挑战流程改为一轮研究质疑和回应

- [ ] 质疑只引用目标 Insight，说明疑点、依据或替代解释；质疑中的新事实同样必须有保存的证据，纯逻辑质疑不强制虚构反证引用。
- [ ] 回应针对疑点给理由，说明维持、修订或撤回。程序维护前后版本关系，避免撤回的旧观点继续支持最终结论。
- [ ] 正常保留“未发现有效反证”的审阅结果并说明审阅范围；不要求为此额外编造负面证据。空数组不能自动表示审阅完成。
- [ ] 不再要求新流程填写 condition ID、风险类型、可验证性分类及测试需求组合；已有可用计算与补证能力按研究需要调用。
- [ ] 质疑或回应失败时保留专项结果，并在综合输入中明确该项未完成审阅。补证复用既有边界，不自动开启无限辩论或额外轮次。

交付：用户可以看出哪个观点被质疑、回应改变了什么；无有效反证与模型失败不会混淆。

主要代码归属：`research/challenge_checks.py`、`research/challenge_reviews.py`、`agents/schemas/_research_dialogue.py`、`graph/native_research.py`、`execution/search_reviews.py`。旧挑战分类仅保留兼容路径。

### 4）精简综合，集中检查最终证据链

- [ ] 综合读取已保存 Insight 及其审阅和修订状态；可读取关联来源片段核对语义，避免仅凭摘要判断。只用可采纳观点支撑结论；待验证观点仅用于说明不确定性。
- [ ] 输出总体判断、关键支持与反对理由、判断局限及可能改变判断的信息。理由引用 Insight；程序追溯到证据片段。综合可以作新推断，但必须展示已保存的依据和推理，不可新增无来源事实。
- [ ] 对最终链条检查引用存在、版本有效、来源与数值可回放。已撤回或排除的观点不能悄然成为肯定依据；相互冲突的已保存事实应可见。
- [ ] 一条理由失效只隔离受影响结论。首轮将总体判断视为一个原子输出：它引用的依据失效则修复或不发布该判断，独立合格 Insight 仍交付；程序不替模型判断哪条理由可以删掉，也不自动补成“中性”。详见 [具体协议](2026-10-28-insight-protocol-design.md)。
- [ ] 去除新流程对固定四维齐备、每项挑战逐格裁决及巨大动态 schema 的依赖。保留正常结构化输出；候选引用由程序解析，不把全部证据候选反复展开到 schema。

交付：综合 Agent 作研究判断，程序决定哪些链条满足发布条件；不以机械计数自动替代研究判断。

主要代码归属：`research/synthesis_sections.py`、`research/report_delivery.py`、`execution/native_publication.py`、`graph/native_research.py`。需要新的窄发布契约，避免复用旧发布入口时暗中恢复全部旧规则。

### 5）同步报告、兼容与验收，再决定切换

- [ ] Reader 和 Markdown 展示一致：判断 → 支持/反对 Insight → 来源与片段；数值可看输入、公式、单位和期间。缺口区分资料不足、模型输出失败、程序故障。
- [ ] 单独展示研究可用性和可选解释状态；移除研究验收对解释全覆盖的要求。原始 Agent 输出的可读性纳入研究内容评估。
- [ ] 使用已有保存资料建立离线对照集，覆盖正常、多来源冲突、部分失败、没有有效反证、来源失效及修订撤回。原始运行数据只读，不改写历史。
- [ ] 对新旧身份、旧记录读取、取消/超时/恢复、预算和跨公司隔离做针对性回归；更新 API/前端与构建资产，以及架构、研究契约、操作说明和必要的中英文 README。
- [ ] 在单独授权后进行有明确次数和预算的真实验收，对比旧链路的有效 Insight、引用准确性、质疑价值、最终判断、局部保留、输入规模和调用成本。不得只用一次 JSON 探测或成功率数字宣布完成。

交付：新链路的研究样本和追溯证据，兼容旧记录的可回退切换；测试通过不自动授权发布或重启服务。

主要代码归属：`execution/native_runner.py`、`runtime/`、`web/reader_*_projection.py`、`frontend/src/api/contracts.ts`、`frontend/src/components/reader/` 以及当前文档拥有者。前端源代码修改后构建 `tradingagents/web/static/`。

## 5. 验收标准与停止条件

| 检查对象 | 应验证的结果 | 不作为成功证明 |
| --- | --- | --- |
| Insight 质量 | 观点具体，依据与推理相连，区分事实/推断，局限明确；人工抽查有研究价值 | 条目多、字数多、全部字段填满 |
| 最终证据链 | 发布的关键事实可定位保存来源和支持片段；数字口径与计算可复现；不偷用失效观点 | 引用编号存在、JSON 合法 |
| 质疑与综合 | 能讨论替代解释并反映修订；有边界的综合判断或诚实的不评级 | 强制反证数量、强制四维及所有分类齐备 |
| 容错与预算 | 坏条目不抹去好条目，阶段失败保留部分结果，修复和补证有界 | 全部 Agent 都成功、不断重试直到过关 |
| 阅读 | 原始报告可读，用户能追溯；辅助解释失败不影响研究交付 | 白话解释 100% 覆盖 |

遇到以下问题先停在对应边界确认：简化方案仍必须依赖旧复杂 envelope；新判断语义需要改变评级准入条件；必须增加模型/搜索调用预算；必须改变现有用户数据或服务生命周期。它们不应混在普通实现细节里自行决定。

本轮不设凭空的“准确率 95%”门槛，也不承诺具体实施工时；先由第 1 项冻结样例及语义边界，再拆成可估算、可逐项验证的实施任务。

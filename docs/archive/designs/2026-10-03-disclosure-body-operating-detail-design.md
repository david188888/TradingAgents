## 目标与不可破坏的约束

让三个 evidence_v1 研究模式引用实际公告正文和经营披露，帮助读者区分：
公司披露了什么、代码提取了什么、专项看到什么、整体还缺什么。

- 公告标题不能代替正文；投资计划、管理层解释不能自动升级为已经兑现。
- 经营明细取自公司实际披露的行业、产品、业务分部、地区收入/成本/毛利等；
  订单、产能、客户只有实际披露才纳入，不推算未披露内容。
- 披露时间、报告期、单位、证券身份与原文定位必须明确。
- 三表、公告列表、正文与经营表覆盖分别判断。某项失败保留其余合格证据。
- 专项未见某资料只描述专项输入，不能据此认定整个研究没有资料。
- Reader 和 Markdown 读取同一保存记录；打开来源不重新取数或调用模型。
- 延续现有默认、额度、取消、恢复、研究边界与本地整合范围。

`native_research.py`、`ResearchRecordSection.tsx`，以及
[最新整合验收](../reviews/2026-10-03-native-multisource-acceptance.md)。

1. CNINFO 查询保存 `PDF URL`，但原生来源只接入列表字段，正文没有被取得。
2. 八期三表是独立合格来源，不等于产品/业务分部经营表。
3. 专项输入按代码分区，当前未知项保存为 `specialist_unknown:<文字>`，
   不含所属专项；综合及 Reader 因而容易将它理解为全局缺失。
4. `dimension_policy` 的可用维度仍附带一个固定的 missing 原因，
   综合失败时可能错误复述「缺少财务字段」等表述。
5. `SourceContentV1` 单条内容上限 4000 字，正文须按有定位的摘录保存，
   不能通过截断后宣称全文来规避契约。

## 推荐接入设计

### 1. 有界文档取得与保存

在原生 collector 增加官方文档步骤，复用巨潮证券/orgId 与目录查询。
90 天事件目录继续描述原有事件窗口；经营报告单独检索截止前最近一期
正式年报或半年报，回看最多 550 天，不将其伪装成 90 天事件覆盖。

每次最多取得一份经营报告和三份近期事件公告，按代码规则稳定选择、去重：
正式报告优先于摘要；事件优先选择影响经营/项目/治理的公告，排除重复附件。
保存选择规则版本及未取得正文的公告 ID；选中四份不代表全部正文覆盖。
预算不足停止补充，不丢弃先前合格来源。

每份 PDF 下载最多 20 MiB、处理最多 500 页，遵守现有 active deadline。
超限、扫描件、损坏、加密或没有合格文本均给出明确状态。
只下载目录返回且通过允许主机/路径校验的官方附件，不跟随重定向。
HTTP 经 BudgetedSession，文档操作经 durable fetch cache；所有尝试计入
现有 24 capability / 64 HTTP ceilings，不新增隐藏重试。

保存文档 ID、标题、披露日期、URL、PDF 哈希、页数、解析器版本及有界内容。
核对官方目录归属、正文证券代码/发行人和报告期；未来、错票或修订身份
不明的材料不入事实。历史取得的文档不声称拥有未经证明的历史内容快照。
保存受限/失败原因，已保存内容恢复时不重新下载。

### 2. 正文摘录和经营表资格

正文使用 `excerpt`，逐段绑定文档哈希、PDF 页码、章节与截取标志。
有限摘录不是全文覆盖；缺正文仍保留原公告列表。
事实描述为「公司在该页披露……」，不把公司预期或计划写成独立验证事实。

经营表采用确定性解析：识别报告期、单位、表头、分类、行名及数值列，
处理跨页表头和换行行名；仅支持通过离线夹具验证的布局。
保留当期/同期口径，金额与百分比区分，缺值不是零。
行业、产品、地区是不同分类，不跨分类相加；只对声明完整且同口径的分类
检查合计。收入/成本与披露毛利率按披露精度检查，不强制凑齐未披露行。
模糊列、缺单位、期间混淆或算术不一致时降级相应表，保留可读原文。

每条可用行保存原表文字、原始数值、规范单位、报告期、分类、页码及哈希。
使用独立代码拥有的披露来源 family，避免伪装成 Sina/Tushare 三表。
经营专项读取已资格化的经营行与公司经营陈述，事件专项读取事件正文；
继续隔离两者的草稿。本文不扩大 C1 的封闭三表/量化条件工具集合。

### 3. 缺失范围表达

保存新未知项时带上 code-owned role；保留旧未知项但标记「专项范围未记录」。
模型提示明确各专项只看到证据子集；综合同时读取代码给出的全局覆盖摘要
与按专项标记的未知项。缺失理由由实际状态生成：有财务、缺经营明细，
不能输出「缺少财务资料」；有市场指标、缺基准，不能输出「没有行情」。

Reader 与 Markdown 展示以下三层：

- 已取得的全局来源/事实覆盖。
- 全局尚未取得或资格不足的资料及具体原因。
- 「经营专项待核查」「事件专项待核查」「市场专项待核查」，
  明示这是专项输入或分析范围，不是全局覆盖结论。

可用维度不给出通用 missing 标签。综合未能形成判断时，说明判断/引用不足，
不将已存在的合格数据写成缺失。新来源仍不能自动解决经济挑战或估值不足。

### 4. 兼容与实施落点

新增 PDF/经营表纯解析模块及原生来源适配；调整代码来源 registry、
事实生成、专项分区和覆盖表述；Reader 与 Markdown 保持同源。
尽量复用 research-record-v1 的内容、定位、哈希和 limitations 字段。
需要公开契约变化时先修改 Python schema，再改全部投影与 TypeScript。

新 collector / prompt / 核心上下文绑定新生产版本；原有 v1/v2 运行保留
原 collector 和输入语义，已保存 V0/输出直接重放。旧报告可改善范围标签，
不回填不存在的正文，不因重读而执行新任务。

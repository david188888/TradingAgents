## 第一性原理：产品必须回答的六个问题

1. **研究什么？** 用户的问题是什么，关键概念怎么理解，需要哪类证据才能回答？
2. **当前能判断什么？** 用普通语言表达答案，明确适用范围。
3. **为什么这样判断？** 给出少数真正影响判断的事实及推断关系。
4. **我能核对吗？** 能从判断定位到具体事实、相关原文或字段、时间与口径。
5. **哪里可能错？** 区分反面事实、资料缺口、执行失败及未来观察。
6. **下一步做什么最有价值？** 明确要查的问题、资料、判定条件及改变判断的方式。

每个 agent/代码步骤的必要性，应由其对这些问题的贡献衡量。运行状态、调用数量、引用数量和来源数量都是辅助信息，不能证明经济判断正确。

[上游官方说明](https://github.com/TauricResearch/TradingAgents#tradingagents-framework)描述了专项分析、研究辩论及后续决策角色。本 fork 可以继续利用多角色分工基础；对用户目标的验收还需要单独检查证据相关性、推断支撑、实际核查与真人理解，不能由角色数量替代。

## 已确认问题

### 1. 审计中心没有适配实际原生流程

保存事件记录 6 个 `native.*` 阶段，全部已完成。最后 checkpoint 保存 5 条 `main_analysis` 调用记录：经营、事件、市场、挑战、综合，均 dispatched 并 settled/ok。

审计 API 和浏览器却展示 13 个旧流程角色，所有角色为未执行、0 轮、0 次模型调用；阶段导航还是分析师、证据治理、研究辩论、研究结论、风险辩论、组合审议。

原因有两层：

- `tradingagents/web/audit_projection.py:137` 的角色投影固定遍历旧 `ROLE_REGISTRY`，没有按照研究流程选择原生角色。
- 审计调用数依赖 `model.*` 事件，但本次 259 个事件只有 run、role 和 artifact 事件，没有模型调用事件。仅替换角色标签不能修复调用统计；必须接通真实调用记录与可审计投影。

审计展示 239 个产物，其中 236 个是恢复 checkpoint，另有配置数据、研究记录与最终 Markdown 各一个。恢复文件有工程用途，但不应把这一数量当成读者可阅读的研究成果。

审计中心实际用途是检查一次运行怎么执行、哪里失败、使用什么配置和模型。它目前的术语与信息结构面向工程排查，无法回答普通用户的“每步为什么做、做出了什么”。建议用户入口改为“研究过程与核查”，技术诊断保留次级入口；命名变化必须伴随信息和数据修复。

另外，`NativeResearchPage.tsx:27` 在运行中也展示审计入口，而 `/audit` 只支持终态运行并对非终态返回 409。运行过程入口与终态技术审计需要明确区分。

### 2. 核心正文读取失败被掩盖成笼统资料缺口

本次选择了半年报摘要、半年报、最新子公司上市进展公告三份正文。最后 checkpoint 记录三者均失败：`document_parser_not_installed`。

`tradingagents/dataflows/disclosure_documents_v2.py:301` 在导入 pypdf 失败时产生该错误。`pyproject.toml` 将 pypdf 放在 china 可选依赖中。该运行没有成功提取这些正文，因此不能从本次结果认定官方资料不存在或公司没有相关业务。

报告正确保留“不足以确认”和“缺少披露不等于关联不存在”的边界；但没有把可修复的运行故障解释给用户。三项本地证据检查中，经营披露和现金流桥不可用，估值背景通过。独立新增来源验证记录为 0。

应明确区分：未检索、取得失败、取得但解析失败、解析成功但没有所需内容、内容不满足证据资格、内容存在但经济结论仍待验证。系统应在付费分析前检查必要能力，并根据具体问题判断缺失的是核心资料还是辅助资料。

### 3. 引用弹窗保存了可追溯内容，却没有提供可理解的追溯路径

第一条“查看引用（3）”打开后约 4213 字符，来源分别为财务字段、行业候选、同行估值。首屏直接显示多期英文 JSON 字段、长数字和技术来源名。

`ResearchRecordSection.tsx:54` 直接通过 `<pre>{content.text}</pre>` 展示保存内容，随后显示时间和 SHA256。用户需要先理解数据结构，才能知道某个字段与判断有什么关系。

引用机制验证来源绑定与资格，不等于已经证明每个来源都能支持这条经济推断。这里缺少“相关字段/段落在哪里”“直接证明什么”“不能证明什么”的展示和检查。同行估值与经营关联问题的关系尤其需要解释；不能仅凭来源附着在某条 claim 上就宣称它证明了业务关联。

建议引用默认展示：当前核对的问题 → 支撑事实 → 对应原文/字段 → 对判断的作用及限制 → 来源和报告期。金额转换成中文单位，英文键映射为中文。原始数据、哈希和完整技术记录按需展开；解释必须来自已保存的结构化事实及绑定，打开引用不产生新的事实或模型总结。

### 4. 研究判断、依据和未知项重复，并缺少阅读层级

实际大段结论占据最强视觉位置，“研究判断”和“关键依据”等标题相对很小。当前 CSS 专门设置了大结论和估值/量化卡片，但大部分其他内容仍依赖默认标题与段落样式。实际 DOM 测得 h3 约 15.21px，h4 与基础正文约 13px，结论 20–25.6px。

最前面的关键依据再次重复“无法确认”，另两条主要是待验证条件。读者难以迅速找到已经取得的具体事实。疑点、挑战、未知项和覆盖限制又用不同术语复述类似缺口。

底层 assessment 为 `completeness=complete`、`quality=LOW_CONFIDENCE`。`NativeAssessment` 只要 LOW_CONFIDENCE 就显示“本次判断为部分研究”，合并了两个不同字段的含义。界面应分别表达执行状态、已回答范围及证据限制，不将它们压成一个完成/部分标签。

当前报告缺少局部概念说明。“现金流桥”“合并口径”“经济判断”“专项”“挑战”等词需要在读者遇到它们时解释，并说明它们为什么与本次问题有关。

### 5. 运行页提供角色状态，未解释步骤目的与产物

`NativeResearchPage.tsx:34` 之后只有状态说明、六行列表和取消按钮。无法看出此步的问题、输入、形成的结构化成果、遇到的阻塞以及接下来发生什么。大片空白来自信息组织不足，不能仅用增加装饰解决。

建议阶段展示“此步要回答什么 / 已得到什么 / 还有什么缺口”，并让用户打开已保存且可公开的产物。展示事实、假设、反面证据和核查结果即可，不需要展示模型内部思维过程。阶段完成不能写成对应问题已经解决。

### 6. 流程对当前问题的适配不足

本次用户问题是公司的主营业务与 AI 供应链是否具有实质联系。关键证据应是产品应用、客户、订单、相关收入规模及供应链位置。

报告下一步同时建议补 AI 基准来计算 Beta/相关性。股价一起涨跌只能描述市场联动，不能证明业务、客户或收入的实质联系。把它作为业务关联判断的必要核查容易带偏读者。

“不能确认关联”与“反面证据证明关联弱”必须分开；“未能取得正文”与“正文没有相关披露”也必须分开。本次属于证据获取存在故障、关键问题未得到充分回答，不能包装成对公司的全面否定。

固定三专项的结构有隔离和反面检查价值，但每个专项需要围绕当前问题交付互补成果。更深的任务路由变更需另行设计和对照验收，不能由页面改版顺带完成。

## 三种优化路径

| 路径 | 优点 | 代价与不足 |
| --- | --- | --- |
| **围绕研究问题组织报告，并同步修复证据解释和真实过程记录（推荐）** | 直接服务理解、追溯和判断；保留既有内核与满意的估值/量化部分 | 涉及 Reader 投影、证据绑定解释和可观测性；不能只改 CSS |
| 先修视觉样式 | 更快改善字体、标题、间距和分区 | 0 调用、正文故障和推断重复仍在，无法解决主要问题 |
| 整体改为按问题动态组织 agent | 长期可能减少无关步骤和重复分析 | 路由、预算、恢复、角色隔离及对照验收变更较大，不适合先行推进 |

建议先执行报告、证据与过程的同步优化。动态组织中的“每步应说明新增贡献”原则可用于检查交付，但动态调度本身留到有实际对照证据时决定。这是实施路径选择，与下文草图的 A/B 阅读布局分别讨论。

## 待讨论的阅读结构

以下是设计中的信息结构；用户已确认问题优先及 B 双栏方向，具体表达仍在评审，不是实施规格。

- **报告**：研究问题、简短答案、少数关键事实、事实到判断的解释、主要疑点、下一步；保留估值与量化背景，并标明它们与当前问题的关系。
- **证据**：从当前判断直接进入相关事实和原文，而非先进入来源仓库。术语解释嵌入当前阅读上下文。
- **研究过程**：阶段目的、输入范围、公开产物、执行与回答状态、阻塞原因；技术配置、原始输入和恢复快照在次级区域。

标题字号、正文大小、行长、留白和区域边界按阅读层级整体设计。先判断哪些内容应常驻，再选卡片、分隔线和展开方式。左侧新建研究配置在阅读已完成报告时可收起，让报告拥有清晰的工作区域。

示例：本次报告应让读者立即明白“本次尚不能回答 AI 业务贡献是否显著；已取得合并财务与公告目录，但三份正文解析失败，因此还缺产品、客户和相关收入依据”。这是一段基于已核实运行状态的示例解释，不是新增公司研究结论。

## Agent 有效性与必要性检查

| 步骤 | 必须交付的公开成果 | 如何判断它有用 |
| --- | --- | --- |
| 证据收集与资格校验（代码） | 当前问题的证据需求表、可用资料、明确失败和时间口径 | 核心资料真的读到了；故障不会被当成经济事实 |
| 经营专项 | 业务链及财务支撑、事实与推断区别 | 给出业务关联的新事实或明确哪一环缺证据 |
| 事件专项 | 事件、发生状态、业务影响路径 | 超过标题复述，说明变化如何影响本次问题 |
| 市场专项 | 价格/风险背景及适用范围 | 提供独立背景，并明确不能证明业务因果 |
| 独立挑战 | 指向具体假设的反面事实、替代解释及可执行核查 | 不重复一句“资料不足”；反面事实与资料缺口分开 |
| 有界核查（代码/工具） | 已执行项目、输入版本、结果和失败原因 | 拟核查与已执行分开；检查通过不自动证明整个经济命题 |
| 综合 | 对研究问题的回答、依据、边界和下一步 | 无新增无来源事实，不以角色多数或运行成功提高置信度 |

## 建议交付顺序与验收

1. **先修真实性**：原生审计角色/阶段、调用来源、正文依赖自检、失败原因解释。兼容历史记录，无法恢复的历史统计显示未记录，不伪造 0；数据请求、HTTP 尝试和模型调用分开计数。
2. **再改报告与证据阅读**：短结论、具体事实、推断说明、相关证据定位、术语解释及风险/缺口分类。保持已保存记录为权威，旧记录缺少解释绑定时诚实降级。
3. **补运行过程**：有界阶段目的、公开产物和阻塞信息；响应式布局与基础可访问性一起验收。
4. **开展真人阅读与研究质量检查**：不能以 DOM 正确、引用可打开或测试通过替代这两项验收。

建议验收用已保存本次运行与离线案例先做，不自动发起新的付费研究：

- 本次 6 个原生阶段和账本 5 次主分析调用在页面正确反映；真实 0 与未记录明确区分。
- 3 个正文失败说明“解析依赖缺失”，不会表述为官方资料不存在。
- 首次打开关键依据，能看到相关中文事实、报告期、单位及支持范围；技术 JSON 不占据首屏。
- 没有已执行独立来源验证的记录，不会显示已完成实证验证。
- 一个读者能在一分钟内说清研究问题、当前答案、关键依据、最大缺口和下一步。
- 一个读者能沿某条判断找到具体字段/原文，并解释它能证明什么、不能证明什么。
- 在一般桌面与手机视口、放大文字、键盘操作下验证阅读顺序；Jev 在超高视口完成不能替代这些检查。
- 新数据不足、解析失败、证据冲突及历史缺字段分别有明确展示，不以统一“部分研究”掩盖原因。

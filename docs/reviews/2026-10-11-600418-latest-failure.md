## 为什么前置修复没有拦住

`execution/native_model.py:_parse` 检查提议 schema 和 `supporting_fact_ids` 是否属于专项输入，却不检查可执行条件的证据/指标是否属于该假设。修复后的提议因此能通过适配层并缓存。

`graph/native_research.py:_call` 保存提议、结算预算并记录阶段完成；合并时才检查条件依赖闭合并抛异常。于是 UI 同时显示专项已完成和运行失败。

`web/manager.py:_error_category` 将所有 ValueError/KeyError 映射为 `missing_configuration`，造成误导。此错误应有明确的研究提议/引用校验分类，而非通过降低证据规则解决。

## 页面问题

- `/reader/record` 返回 `unavailable / not_published`。不存在本次可读最终报告。
- `/reader/process` 和专项端点仍返回 `publication_pending / pending_publication`。失败后“等待发布”没有表达终止状态。
- `ReaderAgentOutput.tsx` 对不可读产物统一追加“最终报告仍可按原保存记录阅读”，与本次未发布记录矛盾。
- `nativeReader.css` 的颜色变量及大部分排版/按钮规则限定在 `.question-reader`，而失败/进行中页面和专项详情位于其外。样式共享没有覆盖这些页面。
- 专项卡片排列成单一长列表，没有表达共同输入、并行分工、汇合和停止位置。
